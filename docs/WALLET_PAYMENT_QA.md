# QA кошелька и платежей

Документ описывает, как проверять денежные сценарии платформы, пока реальный
эквайринг не подключен.

## Область проверки

В проверку входит:

- Пополнение кошелька клиента.
- Заявка клиента на вывод средств.
- Резервирование оплаты по заказу.
- Выплата эксперту после завершения заказа.
- Возврат клиенту при отклонении работы.
- Покупка готовой работы из магазина.
- Учет комиссии платформы в финансовом журнале.

Пока не входит в проверку:

- Реальные ключи эквайринга Альфа-Банка/СБП.
- Реальное исполнение банковского перевода после создания заявки на вывод.
- Массовое подтверждение выплат через отдельные админские экраны.

## Локальный эмулятор кошелька

Локальный Docker запускается с `PAYMENTS_SANDBOX=True` в `docker-compose.dev.yml`.

Санбокс-пополнения специально ограничены:

- Сотрудники (`is_staff=True`) могут пополнять кошелек мгновенно.
- Пользователи с email на `@okoznaniy.test` могут пополнять кошелек мгновенно.
- Обычные пользователи с production-похожими email требуют настроенного провайдера.

Пример API-smoke:

```http
POST /api/wallet/topup/
{
  "amount": "500.00",
  "payment_method": "sberpay_qr"
}
```

Ожидаемый результат в санбоксе:

- В ответе есть `"sandbox": true`.
- `Payment.status` становится `completed`.
- Создается одна запись `Transaction(type=topup)`.
- `User.balance` увеличивается один раз, даже если завершенный платеж сохранится повторно.

## Правила финансового журнала

Каждое внутреннее движение денег должно создавать запись транзакции.

- `topup`: увеличивает `User.balance`.
- `hold`: увеличивает `User.frozen_balance`, доступный остаток уменьшается.
- `release`: уменьшает `balance` и `frozen_balance` клиента.
- `payout`: увеличивает `balance` эксперта.
- `commission`: увеличивает баланс системного пользователя `_system_commission`.
- `refund`: уменьшает `User.frozen_balance`, доступный остаток возвращается клиенту.
- `purchase`: сразу уменьшает `balance` покупателя.
- `withdrawal`: уменьшает `balance` пользователя и создает заявку на вывод.

Формула активного резерва по заказу:

```text
active_order_hold = HOLD - RELEASE - REFUND
```

Формула всегда должна считаться в рамках конкретного заказа и клиента этого заказа.

## Сценарии оплаты заказа

### Внешний callback оплаты заказа

Когда платежный провайдер подтверждает оплату заказа:

1. `Payment` становится `completed`.
2. Клиент получает запись `topup` на оплаченную сумму.
3. Та же сумма уходит в `hold` по заказу.
4. Заказ переходит в `in_progress`.

Callback должен быть идемпотентным:

- Повторный callback не должен создавать второй `topup`.
- Повторный callback не должен создавать второй `hold`.

### Клиент принимает работу

Предусловия:

- Заказ находится в статусе `review`.
- По заказу есть активный резерв.

Ожидаемый результат:

- Заказ переходит в `completed`.
- `balance` клиента уменьшается на сумму резерва.
- `frozen_balance` клиента уменьшается на сумму резерва.
- Эксперт получает выплату за вычетом комиссии платформы.
- `_system_commission` получает комиссию платформы.

### Клиент отклоняет работу

Предусловия:

- Заказ находится в статусе `review`.
- По заказу есть активный резерв.

Ожидаемый результат:

- Заказ переходит в `cancelled`.
- `frozen_balance` клиента уменьшается.
- Доступный остаток клиента восстанавливается.
- Эксперт не получает выплату.

## Сценарий покупки готовой работы

Покупка готовой работы создает заказ, но деньги все равно должны проходить через
кошелек.

Предусловия:

- Готовая работа имеет статус `approved` и активна.
- Покупатель не является автором работы.
- У покупателя достаточно доступного баланса.

Ожидаемый результат:

- Баланс покупателя уменьшается на стоимость работы.
- Эксперт получает стоимость работы за вычетом комиссии.
- `_system_commission` получает комиссию.
- Создается заказ со статусом `in_progress`.
- Покупка связывается с этим заказом.
- Транзакции `purchase`, `payout` и `commission` связаны с заказом.

Если у покупателя недостаточно средств:

- API возвращает `400`.
- Покупка не создается.
- Заказ не остается в базе.
- Транзакции не создаются.

## Сценарий вывода средств

Предусловия:

- У пользователя достаточно доступного баланса.
- Номер карты проходит валидацию.

Ожидаемый результат:

- Баланс пользователя уменьшается сразу.
- Создается `Transaction(type=withdrawal)`.
- Создается `WithdrawalRequest(status=pending)`.
- Реальный перевод пока выполняется вручную, вне приложения.

## Команды автопроверки

Backend-проверки:

```powershell
docker compose -f docker-compose.dev.yml exec -T backend python manage.py test apps.wallet.tests apps.shop.tests --keepdb --verbosity 1
docker compose -f docker-compose.dev.yml exec -T backend python manage.py check
```

Опциональный полный прогон backend-тестов:

```powershell
docker compose -f docker-compose.dev.yml exec -T backend python manage.py test --keepdb --verbosity 1
```

## Текущие известные ограничения

- Проверка реального callback эквайринга все еще зависит от ключей провайдера и
  должна отдельно проходить на staging.
- Подтверждение заявки на вывод сейчас является ручной/админской операцией:
  реальный банковский API пока не подключен.
- В части старых backend-файлов остаются русские строки с битой кодировкой.
  Они не блокируют тесты финансового журнала, но их нужно почистить отдельным
  проходом по кодировке.
