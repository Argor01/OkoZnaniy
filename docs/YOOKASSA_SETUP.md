# Подключение ЮKassa

Эквайринг ЮKassa (API v3). Код: `apps/payments/providers/yookassa.py`.

ЮKassa — агрегатор, а не банк: плательщик выбирает карту, СБП, ЮMoney или
SberPay уже на её платёжной форме. Поэтому у нас один способ оплаты
`yookassa`, а не отдельный пункт под каждый инструмент.

## Что нужно из личного кабинета

Тестовый магазин требует ровно двух значений:

| Переменная | Где взять | Вид |
|---|---|---|
| `YOOKASSA_SHOP_ID` | Настройки → Магазин, переключиться на тестовый магазин | `123456` |
| `YOOKASSA_SECRET_KEY` | Настройки → Ключи API → «Выпустить тестовый ключ» | `test_...` |

У тестового магазина **свой shopId**, он не совпадает с боевым. Адрес API
общий для обоих контуров — тестовость определяет префикс ключа `test_`.
Переход на бой — это замена пары значений, менять код не нужно.

## Настройка

В `.env` на сервере:

```
YOOKASSA_SHOP_ID=<shopId тестового магазина>
YOOKASSA_SECRET_KEY=<test_...>
YOOKASSA_RETURN_URL=https://okoznaniy.ru/payment/result
```

Чтобы кнопка «Оплатить картой» пошла через ЮKassa, а не через Уралсиб:

```
CARD_ACQUIRER=yookassa
```

Отдельный пункт «ЮKassa» в списке способов оплаты работает независимо от
`CARD_ACQUIRER` — он всегда идёт в ЮKassa.

После правки `.env`:

```bash
docker compose up -d --build backend celery
```

## Уведомления

В кабинете: Настройки → Уведомления (HTTP-уведомления), адрес:

```
https://okoznaniy.ru/api/payments/yookassa/callback/
```

Работает и длинный вариант `/api/payments/payments/yookassa/callback/`:
роутер DRF подключён под префиксом `payments/`, а приложение — под
`api/payments/`, поэтому его собственные маршруты получают этот сегмент
дважды (так же выглядит колбэк Уралсиба). Для внешнего адреса оставлен
короткий путь — повторяющийся сегмент в кабинете только провоцирует
ошибку.

События: `payment.succeeded`, `payment.canceled`, `refund.succeeded`.

Подписи у уведомлений ЮKassa нет — проверять нечего. Поэтому доверие
строится на двух рубежах:

1. адрес отправителя должен принадлежать [сетям ЮKassa](https://yookassa.ru/developers/using-api/webhooks)
   (список в `TRUSTED_NETWORKS`, проверяется по `X-Real-IP` от nginx —
   `X-Forwarded-For` для этого не годится, его начало подделывает клиент);
2. решение об оплате принимается только после запроса `GET /v3/payments/{id}`.
   Тело уведомления не источник правды: оно может быть подделано или
   устареть.

Коды ответа выбраны под ретраи ЮKassa: всё, что не 2xx, она повторяет
сутки. Поэтому 500 отдаём только при сбое на нашей стороне, а на чужой или
неактуальный платёж — 200, чтобы не собирать бесконечные повторы.

## Ставка эквайринга

ЮKassa удерживает свою комиссию из поступившего платежа: при списании
101,50 ₽ в поле `income_amount` вернулось 97,95 ₽, то есть **3,5%**.
Площадка же выставляла клиенту 1,5% и доплачивала разницу из своей доли.

Теперь ставок две, и обе настраиваются окружением:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `ACQUIRING_FEE_PERCENT` | `3.5` | Приём платежа. Добавляется **сверху** к заказу или пополнению, платит клиент |
| `PAYOUT_ACQUIRING_FEE_PERCENT` | `1.5` | Перевод на карту при выводе. Удерживается из суммы вывода |

Разделение принципиальное: приём и выплаты тарифицируются по разным
договорам, и общая константа означала бы, что подъём ставки эквайринга
молча удорожает вывод денег авторам.

Сверьте `ACQUIRING_FEE_PERCENT` со своим тарифом в кабинете: 3,5% —
это то, что удержал тестовый магазин, у боевого договора ставка может
отличаться.

### Проценты больше не зашиты в интерфейс

Разбивку суммы отдаёт `GET /api/wallet/quote/?amount=1000&kind=order|topup`:

```json
{"base_amount": "1000.00", "service_fee": "250.00", "service_fee_percent": "25",
 "acquiring_fee": "43.75", "acquiring_fee_percent": "3.5", "total": "1293.75"}
```

Раньше окно оплаты умножало сумму на зашитые 25% и 1,5%. Это ломалось
уже дважды: у клиентов с индивидуальной ставкой сервисного сбора
интерфейс показывал не ту сумму, и любое изменение ставки требовало
правки в двух местах. Теперь считает только сервер.

## Тестовый магазин закрыт для клиентов

Ключ вида `test_*` создаёт платежи, которые ничего не списывают, но
возвращаются к нам успешными и зачисляются на кошелёк. Поэтому пока
подключён тестовый магазин, платить через ЮKassa могут только сотрудники
(`is_staff`) и учётки с почтой `@okoznaniy.test`. Остальные видят
«Оплата через ЮKassa временно недоступна».

Проверка привязана к префиксу ключа, а не к отдельному флагу: забыть
переключить флаг легко, подменить ключ незаметно — нет. Как только в
`.env` окажется боевой ключ, оплата откроется всем сама.

Запрет закрывает обе двери: и способ оплаты `yookassa`, и карточную
рельсу при `CARD_ACQUIRER=yookassa`.

## Защита от двойного списания

Каждый `POST` уходит с заголовком `Idempotence-Key`, выведенным из нашего
`payment_id` через `uuid5`. Одна запись `Payment` соответствует ровно
одному платежу в ЮKassa: повторный вызов при потерянном ответе вернёт уже
созданный платёж, а не спишет деньги второй раз.

Обратная сторона: если платёж по этому ключу уже отменён, ЮKassa вернёт
его же, без ссылки на форму, и пользователь увидит ошибку. Это осознанный
размен — лучше ошибка, чем двойное списание. Новая попытка оплаты создаёт
новую запись `Payment` и, значит, новый ключ.

## Что проверяется тестами

`apps/payments/tests_yookassa.py` (31 тест):

- создание платежа уходит с Basic-авторизацией и `Idempotence-Key`,
  сумма — строкой с двумя знаками, а не копейками, как в RBS;
- ключ идемпотентности стабилен для одной записи `Payment`;
- уведомление об успехе не проходит, если API отвечает `pending` —
  подделать зачисление телом уведомления нельзя;
- недоплаченный платёж не зачисляется;
- отменённый помечается `failed`, возвращённый — `refunded`;
- уведомление с чужого адреса получает 403;
- сбой шлюза отдаёт 500, чтобы ЮKassa повторила доставку;
- `X-Forwarded-For` от клиента не подменяет отправителя;
- `CARD_ACQUIRER=yookassa` уводит карточную рельсу в ЮKassa, а
  RBS-эндпоинт при этом перестаёт обслуживать карточные платежи;
- статус платежа отдаётся только владельцу: по чужому `payment_id`
  страница возврата получает 404;
- в тестовый магазин пускает только сотрудников и `@okoznaniy.test`,
  а боевой ключ открывает оплату всем.

Запуск:

```bash
docker compose exec -T backend python manage.py test apps.payments.tests_yookassa
```

## Чего здесь пока нет

- **Чеки по 54-ФЗ.** Состав чека в платёж не передаётся. Если у магазина
  включена фискализация через ЮKassa, в `register_payment` нужно добавить
  объект `receipt` со ставкой НДС и признаком предмета расчёта.
- **Выплаты экспертам.** «Выплаты» — отдельный продукт ЮKassa с отдельным
  договором и ключом; в тестовом магазине не проверяются. Вывод средств
  (`apps/wallet`) работает по-прежнему.
- **Двухстадийная оплата.** Платежи создаются с `capture: true`:
  удержание и списание одной операцией. Эскроу у нас живёт во внутреннем
  кошельке, дублировать его на стороне банка не нужно.
